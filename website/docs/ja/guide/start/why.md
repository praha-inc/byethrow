# byethrow を選ぶ理由

このページでは、`Result` 型が解決する課題と、日々の TypeScript プロジェクトに byethrow が特に適している理由を説明します。

## `try/catch` の課題

JavaScript ではどの関数もいつでも例外を投げられますが、TypeScript は関数が何を投げるかを表現できません。
その結果、いくつかの問題が生じます。

- **見えない失敗**：関数のシグネチャからは失敗する可能性がわからないため、エラー処理を忘れやすくなります。
- **型のないエラー**：`catch` ブロックで受け取る値は常に `unknown` なので、その正体を推測するしかありません。
- **絡み合う制御フロー**：`try/catch` ブロックがエラー処理とビジネスロジックを混在させ、正常系の流れが追いにくくなります。

`Result` 型は、失敗を通常の戻り値として扱うことでこれらの問題を解決します。

- **明示的**：失敗が戻り値の型の一部になるため、処理し忘れるとコンパイラが教えてくれます。
- **型付き**：各エラーは、処理される場所まで正確な型を保ちます。
- **合成可能**：処理をつなげることができ、失敗すると残りのステップは自動的にスキップされます。
- **分離**：ビジネスロジックは一直線に読めるようになり、エラー処理は 1 か所にまとまります。

## 他のライブラリではなく byethrow を選ぶ理由

TypeScript のエコシステムには、優れた Result ライブラリがいくつもあります。
byethrow は、最小限のユーティリティと本格的な関数型プログラミングのフレームワークの間にある、ちょうどよいバランスを目指しています。

### neverthrow との比較

neverthrow は結果をメソッドを持つクラスのインスタンスとして表現し、`Result` と `ResultAsync` という別々のクラスを提供しています。
byethrow は異なるトレードオフを選んでいます。

- **プレーンオブジェクト**：byethrow の `Result` はただの `{ type, value }` または `{ type, error }` というオブジェクトなので、そのままログ出力、シリアライズ、比較ができます。
- **独立した関数**：各操作は `pipe` で組み合わせる独立した関数なので、使わない関数はツリーシェイキングで取り除かれます。
- **同期と非同期で同じ API**：同じ関数が `Result` と `Promise<Result>` の両方で動作するため、2 種類の `Result` を変換し合う必要がありません。
- **充実した部品**：オブジェクトを組み立てる `bind`、すべてのエラーを集める `collect`、[Standard Schema](https://standardschema.dev/) でバリデーションする `parse` など、実際の開発でよく必要になる関数が揃っています。

### Effect や fp-ts との比較

Effect や fp-ts は非常に強力ですが、独自のランタイムモデルと、関数型プログラミングの多くの概念を伴います。
byethrow が扱うのは成功と失敗だけなので、チームは新しいプログラミングパラダイムを学ばずに導入できます。

## 実際の開発を想定した設計

- **チームにやさしい**：関数単位で少しずつ導入でき、例外を投げる既存のコードとも共存できます。
- **TypeScript ファースト**：パイプラインのすべてのステップで、成功値とエラーの型が推論されます。
- **軽量**：小さなランタイムで、ツリーシェイキングに完全に対応しています。
- **予測しやすい**：`map` / `mapError`、`andThen` / `orElse` のような一貫した命名規則により、API を覚えやすくなっています。
- **周辺ツールが充実**：[Linter プラグイン](../ecosystem/linter/index)、[テストマッチャー](../ecosystem/testing)、[AI アシスタント向けドキュメント](../ecosystem/llm-integration)によって、チーム全体が同じパターンに従えます。
