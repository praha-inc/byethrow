# Custom Error

Any value can be used as the error of a `Result`, but plain strings and generic `Error` objects make it hard for callers to tell failures apart.
We strongly recommend giving each kind of failure its own error type.
This page explains the options and how to create custom errors efficiently.

## Two Ways to Define Custom Errors

### 1. Error Classes (Recommended)

Define a class that extends the built-in `Error` class, and give it a unique `name`:

```ts
import { Result } from '@praha/byethrow';
import { z } from 'zod';

class ValidationError extends Error {
  override readonly name = 'ValidationError';
}

const validateEmail = (email: string): Result.Result<string, ValidationError> => {
  return Result.pipe(
    email,
    Result.parse(z.email()),
    Result.mapError((issues) => new ValidationError('Invalid email format', { cause: issues })),
  );
};
```

### 2. Tagged Objects

Alternatively, use plain objects with a property that identifies the kind of error:

```ts
import { Result } from '@praha/byethrow';
import { z } from 'zod';

type ValidationError = {
  type: 'ValidationError';
  message: string;
  value: string;
};

const validateEmail = (email: string): Result.Result<string, ValidationError> => {
  return Result.pipe(
    email,
    Result.parse(z.email()),
    Result.mapError(() => ({
      type: 'ValidationError',
      message: 'Invalid email format',
      value: email,
    })),
  );
};
```

## Why We Recommend Error Classes

Both approaches let callers distinguish errors, but error classes have several practical advantages.

### Stack Traces and Error Chaining

An `Error` records a stack trace showing where it was created, and the `cause` option keeps the original error that led to it.
Together, they make debugging much easier:

```ts
type User = { id: string; name: string };
declare const database: { findUser: (id: string) => Promise<User> };
// ---cut-before---
import { Result } from '@praha/byethrow';

class DatabaseError extends Error {
  override readonly name = 'DatabaseError';
}

const fetchUser = (id: string) => Result.try({
  try: () => database.findUser(id),
  // The stack trace points here, and the original error is kept as `cause`
  catch: (error) => new DatabaseError('Failed to fetch user', { cause: error }),
});
```

### Compatibility with `throw`

Errors in a `Result` sometimes end up being thrown, for example by [`unwrap`](../tutorial/resolving/unwrapping) at the boundary of your application.
Error monitoring tools and runtimes expect thrown values to be `Error` instances. A thrown plain object has no stack trace and is often reported poorly.

## Recommended: Using `@praha/error-factory`

Writing error classes by hand quickly becomes repetitive.
[`@praha/error-factory`](https://github.com/praha-inc/error-factory) reduces the boilerplate and keeps your errors consistent.

### Defining Errors

Extend the class returned by `ErrorFactory`.
The `name` becomes a literal type, which lets TypeScript narrow unions of errors by their `name`:

```ts
import { ErrorFactory } from '@praha/error-factory';

class ValidationError extends ErrorFactory({
  name: 'ValidationError',
  message: 'Invalid input provided',
}) {}

class QueryError extends ErrorFactory({
  name: 'QueryError',
  message: 'An error occurred while executing a query',
  // Additional fields carried by the error
  fields: ErrorFactory.fields<{ query: string }>(),
}) {}

class NotFoundError extends ErrorFactory({
  name: 'NotFoundError',
  message: 'Resource not found',
}) {}
```

`message` can also be a function that builds the message from the fields:

```ts
import { ErrorFactory } from '@praha/error-factory';

class HttpError extends ErrorFactory({
  name: 'HttpError',
  message: ({ status }) => `Request failed with status ${status}`,
  fields: ErrorFactory.fields<{ status: number }>(),
}) {}
```

### Using Errors in Results

Create the errors wherever a failure occurs, passing the original error as `cause` and filling in any fields:

```ts
import { ErrorFactory } from '@praha/error-factory';

class ValidationError extends ErrorFactory({
  name: 'ValidationError',
  message: 'Invalid input provided',
}) {}

class QueryError extends ErrorFactory({
  name: 'QueryError',
  message: 'An error occurred while executing a query',
  fields: ErrorFactory.fields<{ query: string }>(),
}) {}

class NotFoundError extends ErrorFactory({
  name: 'NotFoundError',
  message: 'Resource not found',
}) {}

type UserRow = { id: string; name: string };
declare const database: { query: (sql: string, params: unknown[]) => Promise<UserRow | undefined> };
// ---cut-before---
import { Result } from '@praha/byethrow';
import { z } from 'zod';

const validateId = (id: string) => {
  return Result.pipe(
    id,
    Result.parse(z.string().startsWith('u')),
    Result.mapError((issues) => new ValidationError({ cause: issues })),
  );
};

const executeQuery = (sql: string, params: unknown[]) => {
  return Result.try({
    try: () => database.query(sql, params),
    catch: (error) => new QueryError({ query: sql, cause: error }),
  });
};

const findUser = (id: string) => {
  return Result.pipe(
    validateId(id),
    Result.andThen((id) => executeQuery('SELECT * FROM users WHERE id = ?', [id])),
    Result.andThen((row) => {
      if (!row) {
        return Result.fail(new NotFoundError());
      }
      return Result.succeed({ id: row.id, name: row.name });
    }),
  );
};
// Type: (id: string) => Result.ResultAsync<{ id: string; name: string }, ValidationError | QueryError | NotFoundError>
```

### Handling Errors

Because each error has a literal `name`, a `switch` statement narrows the error to its exact class, including its fields:

```ts
import { Result } from '@praha/byethrow';
import { ErrorFactory } from '@praha/error-factory';

class ValidationError extends ErrorFactory({
  name: 'ValidationError',
  message: 'Invalid input provided',
}) {}

class QueryError extends ErrorFactory({
  name: 'QueryError',
  message: 'An error occurred while executing a query',
  fields: ErrorFactory.fields<{ query: string }>(),
}) {}

class NotFoundError extends ErrorFactory({
  name: 'NotFoundError',
  message: 'Resource not found',
}) {}

declare const findUser: (id: string) => Result.ResultAsync<{ id: string; name: string }, ValidationError | QueryError | NotFoundError>;
// ---cut-before---
const result = await findUser('u123');

if (Result.isSuccess(result)) {
  console.log(result.value);
} else {
  switch (result.error.name) {
    case 'ValidationError':
      console.error('Validation error:', result.error.message);
      break;
    case 'QueryError':
      // Narrowed to QueryError, so `query` is available
      console.error('Query error:', result.error.message, 'Query:', result.error.query);
      break;
    case 'NotFoundError':
      console.error('Not found error:', result.error.message);
      break;
  }
}
```

For more ways to handle unions of errors, including exhaustiveness checks, see [Pattern Matching](./pattern-matching).
